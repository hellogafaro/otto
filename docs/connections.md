# Connections backend

Connections owns account associations, private credential references, human configuration, scoped Agent grants, exact operation approvals, and durable execution outcomes. GitHub App and MCP Streamable HTTP adapters run inside the server. They expose no credential-bearing browser or native shell result.

## Public surface

`@otto/connections` exports `createConnection`, `getConnection`, `getConnections`, `updateConnection`, `grantConnectionAccess`, `revokeConnectionAccess`, `disconnectConnection`, `snapshotGrants`, `requestOperation`, `approveOperation`, `getOperation`, `getOperations`, `retryOperation`, and `recoverOperations`. Collection getters take bounded filters. `getOperations(c, {connectionId?, state?, after?, limit?} = {})` returns `{items,next}` across the human's owned Connections when no Connection is specified. Both workspace IDs, current Connection owner and recorded sponsor are filtered before the limit. `state` includes `awaiting_approval`; `after` is an exclusive operation-ID UUID cursor in ascending ID order, and `limit` defaults to 100 with a 100 maximum; a limit+1 query determines the null terminal cursor. An explicit Connection still requires current ownership. Ordinary human members can read their own approvals without administrator-only Connection enumeration; Agents cannot. Listing a historical pending intent never bypasses approval's current grant, Run and audience checks. Operation getters require the current Connection owner and recorded sponsor. Public Connection views omit `accountRef`, `credentialRef`, configuration, discovery internals and provider responses. Operation views omit stored provider output; publication owns its audience.

`@otto/connections/server` exports `createConnectionService`, `createInfisicalResolver`, `recoverConnectionOperations`, `CONNECTION_CONFIG`, `MCP_PROTOCOL_VERSION`, and the server-only boundary and secret-reference types. `createConnectionService` returns `connectConnection`, `discoverConnection`, `requestOperation`, and `executeOperation`. Calling `connectConnection` again refreshes or reconnects the same configured association. Disconnect and configuration edits revoke grants; reconnect never restores them automatically. Model/native-subscription associations remain disconnected without a qualified native adapter.

The required `ConnectionBoundary` has three members:

- `transact(work)` supplies the authenticated workspace transaction with its mutation lock.
- `validateRun(c, {runId, attempt, launchKey, environmentGeneration})` derives the current Agent and checks current Run state, attempt, sponsor, saved inputs/grants/audience and Environment ownership/generation. It returns `{agentId, audience: {humans, agents}}`. The audience must already satisfy the saved Run audience cap and current permissions. Connections then checks every recipient against the grant's explicit audience before and after I/O; the callback cannot expand that grant. Main server composition owns this cross-domain validation; Connections never imports Runs.
- `publishResult(c, {operationId, connectionId, runId, action, target, value, audience})` validates the current output audience and publishes in that same transaction. `operationId` is the stable publication request identity. The callback must use `c.tx`, not perform external I/O or open another transaction.

The Run validator must compare the whole saved/current grant snapshot exactly, including confirmation policy and audience, to preserve the accepted scope; Connections separately guards each current operation. Its argument remains `RunProof`, deliberately constructed without operation arguments. All callbacks are required. Tool input has no `agentId`; strict parsing rejects caller-supplied identity. Connections also compares a trusted agent actor, if present, to the Agent derived by the Run validator. Neither input schemas nor this callback interface authenticate HTTP requests on their own. The main server supplies human sessions and authenticated native tool routing before constructing the boundary.

## Lifecycle and execution

An authorized human creates metadata, updates its explicit configuration/reference, connects, reviews discovery, then grants resources and actions to an Agent. Only the Connection owner can configure/grant/disconnect, and must still be an administrator. Each grant retains its sponsoring human and requires an explicit recipient audience. Humans must be current members and Agents must belong to the workspace. Legacy grants with unknown audiences are excluded from snapshots and denied requests; no audience is guessed. `snapshotGrants` includes the approved audience so Run admission can preserve it with its other input scope. Resources are exact identifiers, not wildcard prefixes. MCP discovery never creates a grant.

An operation identity hashes canonical arguments plus request ID, Run, attempt, launch key, exact normalized audience, Environment generation, derived Agent, sponsor, Connection, account association, action, target, configuration token and grant generation. Exact retries return the original request. Different arguments or authorization scope conflict. Human approval supplies the reviewed identity digest; it cannot approve a mutable ID alone. Pending requests and approvals expire after five minutes. Legacy operation rows without recoverable identities are retained but cannot execute.

Execution claims the approved operation durably before credential or provider I/O, then rechecks the Run, grant, identity and provider capability before the external operation. After I/O, the same checks and publication run in one workspace transaction with result persistence. A claim token fences stale completion. Concurrent duplicate execution cannot issue a second provider write.

The executor never retries a provider request automatically. A lost/invalid write response produces `uncertain / external_outcome_unknown`; a validated response that cannot be published produces `uncertain / result_withheld`. A failed read can be explicitly retried at most twice before approval expiry, with durable retry count and current checks. Uncertain writes cannot be retried through this API; a human must reconcile the external state before authorizing different work. `recoverOperations` retains human administrator authorization. Server startup uses `recoverConnectionOperations(db: Database): Promise<{recovered: number; hasMore: boolean}>` from `@otto/connections/server`, without inventing a user actor or requiring a surviving sponsor. Both share the same transition: claims older than two minutes become failed reads or uncertain writes, with the token cleared and no provider I/O or publication. The server entry selects at most 101 candidates through a partial index, processes at most 100 per call, locks each workspace, and rechecks execution token, state and exact claim age before changing a row. `hasMore` is a bounded backlog hint; main owns subsequent scheduling. Late completions remain fenced, including after sponsor removal.

Each request has a maximum ten-second deadline, 256 KiB output budget, no redirect following and no transport retry. Arguments are capped at 32 KiB. Exact endpoint origins are deployment configuration; normal traffic requires HTTPS. Loopback HTTP requires an explicit fixture/private-service option. A stalled injected resolver is separately bounded. Known credential echoes are rejected before result storage or publication. Raw HTTP bodies, headers and provider errors are never logged or attached to errors.

GitHub installation-token lifetimes are reserved conservatively before issuance, because disconnect can race token creation. `expiresAt` on Connection metadata is the latest possible external token expiry, not a guarantee that a provider will accept the token. Disconnect returns this deadline. Otto immediately blocks future requests; it does not claim provider-side token revocation.

## Concrete provider boundaries

GitHub supports `repository.read`, `issues.read`, and `issues.create`. Configuration pins App ID, installation ID, account ID, and up to 50 repository IDs with their full names. The account association must equal `github:<accountId>:<installationId>`. Connection preparation verifies the installation account and selected-repository mode, signs a short-lived App JWT, requests an installation token with explicit repository IDs/permissions, and verifies the token's repository inventory. Otto action grants and the returned provider permissions must both permit the operation. Returned objects are reduced to the supported repository/issue fields. The pinned REST version is `2026-03-10`, verified against GitHub's [version policy](https://docs.github.com/en/rest/about-the-rest-api/api-versions) and [breaking-change record](https://docs.github.com/en/rest/about-the-rest-api/breaking-changes). The adapter does not consume the removed deprecated issue/repository fields, and the fixture verifies the version header. Token issuance follows the [GitHub App endpoint documentation](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app).

MCP pins the requested `2025-11-25` handshake protocol and supports its [Streamable HTTP JSON/SSE response transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports). The official [version page](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning) identifies `2026-07-28` as current; this implementation deliberately rejects that negotiation rather than guessing compatibility. It uses no MCP SDK dependency. Sessions are short-lived per preparation and closed on completion or discovery failure. A lost session/response never causes a protected tool call to be replayed. A later operation initializes a fresh session. There is no background event stream or SSE resumption, host-local stdio, sampling, elicitation or automatic resource-link fetch.

Trusted human configuration pins each tool name, the top-level argument that must equal the approved target, and whether the tool is read-only. Server annotations cannot weaken this policy. The deployment must only mark a tool read-only when its semantics are trusted; tool discovery is not a proof of tool behavior. Resource reads require an exact configured/discovered URI and reject a response containing another URI. Discovery is bounded to 100 tools/resources and rejects pagination beyond that bound. All tool content remains untrusted data.

Infisical resolution uses the documented [v4 secret retrieval endpoint](https://infisical.com/docs/api-reference/endpoints/secrets/read), with explicit project/environment/path/name, `includeImports=false` and `expandSecretReferences=false`. A deployment-approved binding maps the exact workspace/Connection/reference tuple to that scope. A reference cannot select arbitrary environment variables or manager scopes. The adapter accepts an injected manager access-token callback; it does not depend on BB or its CLI. No verified production Otto scope is configured by this lane.

## Integrated checkpoint

The server now supplies trusted Run/attempt/Environment and saved/current grant/audience validation, exact human approval transports, result publication in the same transaction, and server-owned startup/minute recovery. The final validator remains the narrow RunProof contract above. Domain cursor helpers and queue calls use `advanceCursor` and `startQueue`; shared normalization uses typed errors and paginated discovery without aliases.

The current native Drizzle schema declares the authorization fields and stale-execution index; numbered pre-MVP app migrations are retired. Unknown saved audiences/launch identities fail closed; no historical authority is invented. Complete grant snapshots retain their explicit overflow guards rather than using discovery pagination.
