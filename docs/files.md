# Files

`@otto/files` owns saved uploaded or Agent-generated bytes and their metadata in `files`. A File is one immutable saved output with a title, type, labels, media type, size, digest, human custodian (`ownerId`), optional Agent author (`creatorAgentId`), optional source Run, `user | workspace` visibility, archive state and optional Project. Documents remain separate editable content and Collections stay Document-only. Simple nested Folders organize both (below); a Drive is only a client presentation, with no Drive domain, item graph, shortcuts, versions, sync or trash service. The previous Resource domain, routes, fields and tool name are retired with no aliases.

## Contract

Routes are under `/api/workspaces/:workspaceId`.

| Route | Purpose |
| --- | --- |
| `GET /files` | Bounded discovery: `projectId`, `type`, `query`, `ownerId`, `visibility`, `label`, `archived`, `sort`/`order` (`title`, `createdAt`, `updatedAt`, `byteLength`), `after`, `limit`; see [Discovery lists](lists.md) |
| `PUT /files/:requestId/content` | Save raw bytes up to 100,000,000 (see Uploads): `?title&type&mediaType&visibility&projectId&folderId&label=…`, body `application/octet-stream`; retrying the exact request returns the same File |
| `POST /files` | Small JSON form `{requestId, title, type, labels? (≤30; Documents share the same label rules), projectId?, folderId?, visibility?, mediaType, bytes (base64, within the 1 MiB JSON body cap), sourceRunId?}`; same identity and retry rules |
| `GET /files/:id`, `PATCH /files/:id` | Read; custodian-only `{title?, labels?, visibility?, folderId?}` (a Folder ID or `null` for the top level) without an edit token |
| `GET /files/:id/file` | Stream the immutable bytes after the verified-spool delivery below |
| `POST /files/:id/archive` | Custodian-only `{archived}` |

References use `fileId`/`fileIds`: Skill supporting files (`PUT /skills/:id/files`), Document attachments (`PUT /documents/:id/attachments`), and Chat Message attachments (`fileIds`; the Message body is now strict so a retired `resourceIds` is rejected rather than silently dropped). The discriminator is `file`: Task links `{type: "file", reference}` and share selections/snapshots (`{type: "file", targetId, includeFile}`, `fileType`). The scoped Pi tool is `file.create`. Retired `/resources` routes return 404 and retired `resourceId`/`resourceIds`/`resource` inputs are rejected.

Custodian ownership, `creatorAgentId`, workspace/Project visibility, archive behavior, saved and current source-Run audience caps, the 100,000,000-byte bound, durable intent before storage I/O, digest-bound object keys and post-I/O reauthorization are unchanged by the rename. Native MCP resource identifiers and Connection grant `resources` keep their protocol meaning.

## Uploads and downloads

Capacity is one constant, `MAX_FILE_BYTES` (100,000,000 decimal bytes), also enforced against direct database writes by the CHECK `files_size_<limit>` (`0 ≤ byteLength ≤ limit`). Native push does not re-diff a changed CHECK expression, so the limit is part of the constraint's name: changing the constant changes the name and push replaces the constraint. Bytes above 8 MiB (`SMALL_FILE_BYTES`) never enter memory: Skill materialization, model tools and the sandboxed HTML share preview refuse larger Files (a Skill's supporting files still total at most 8 MiB).

`PUT /files/:requestId/content` is one authenticated request with a raw body. `Content-Length` is optional; a header above the maximum, or a body that overruns it, is refused with 413, and a body that differs from its declared length with 400. The optional `X-Content-SHA256` is only verified; the stored digest is always computed by the server. Authorization, Project, folder placement and the request identity are checked first: a retry whose metadata or declared length conflicts fails 409 before any body byte is read, and a changed body of the same length fails 409 once it has been hashed. The server then reserves disk from a bounded spool, streams the body to a private 0700 file while counting and hashing it, re-authorizes in a short transaction that records the pending intent (digest-bound key), puts the object by streaming the file through the AWS client (no database transaction is open during I/O), and marks it saved after re-authorizing again. A client abort, timeout, storage error or lost acknowledgement leaves the spool removed and at most a hidden pending intent; retrying the same `requestId` resumes it. Every put is verified by streaming the stored bytes back through SHA-256, and a retry or lost acknowledgement is reconciled the same way: storage metadata is never trusted, so a corrupt object is never published and the intent simply stays pending. `folderId` is first placement only: it is not part of the stored identity, and a retry never moves the File or resets later organization.

`HEAD` on both download routes returns the authorized GET headers plus `X-File-Size` and does no storage read and takes no spool. `GET /files/:id/file` and the public frozen `GET /api/shares/:id/file` first stream the stored object into the spool while checking its length and SHA-256 against the saved record, then re-check authority, and only then send bytes (chunked; the size is on the File record). Authority is re-checked before disclosing beyond each 4 MiB or 2 seconds and before the final chunk, so a revoked reader or share gets a truncated response; reads are demand-driven. Bytes already in socket and kernel buffers cannot be recalled (measured: about 17 MB arrived after a revocation committed during a 100 MB delivery on loopback). The spool directory (`UPLOAD_SPOOL_DIR`) must be local to one host and PID namespace: ownership of an abandoned instance directory is proved by its recorded PID and kernel start time, which is meaningless across namespaces. Spool space is reserved before allocation and held until the response finishes, is cancelled, stalls or exceeds its deadline, and every deadline cancels and joins the underlying stream and file before the space is released; when the budget (`UPLOAD_SPOOL_BYTES`) is exhausted the answer is 503 busy. Anonymous share readers may hold at most half of the budget, but never less than one maximum-size File.

Bun's 30 second idle timeout is disabled only on the upload and download routes and replaced by explicit bounds: a total allowance of `TRANSFER_BASE_MS` (default 60000) plus the size at `TRANSFER_MIN_BYTES_PER_SECOND` (default 262144) for receiving, storage reads and writes, spool verification and delivery, and a stall limit of the smaller of 30 seconds and `TRANSFER_BASE_MS` with no progress. Corrupt or truncated storage yields an error and no body. The idle timeout is disabled only once a transfer is admitted (authorized, placed and holding a spool lease), and every admitted transfer response carries `Connection: close`, so a completed, failed or refused transfer never leaves a keep-alive socket without Bun's timeout (Bun cannot re-arm a disabled timeout on a connection). Refusals before admission, such as an unknown file or share, keep Bun's 30 second idle timeout.

## Folders

`folders` (`id, workspaceId, projectId, parentId, createdBy, title, visibility user|workspace, archived`) are human organization of Files and Documents; `folderId` is nullable on both (null = top level) and `parentId` nests up to depth 8. Routes under `/api/workspaces/:workspaceId`:

| Route | Purpose |
| --- | --- |
| `POST /folders` | `{title, parentId?, projectId?, visibility}` strictly; `projectId` defaults to the parent's and is fixed afterwards |
| `GET /folders`, `GET /folders/:id` | List (`parentId`, `root=true`, `projectId`, `archived`, `query`, `visibility`, `createdBy`, `sort`/`order`, `after`, `limit`); read with `path`: the readable ancestors from the top, for breadcrumbs |
| `PATCH /folders/:id` | Creator-only `{title?, parentId? (ID or null), visibility?}` |
| `POST /folders/:id/archive` | Creator-only `{archived}` |
| `GET /library` | Mixed browse: `?folderId=` (omit for the top level of the workspace, or of `projectId`), `archived`, `query`, `label`, `sort`/`order` (inside each kind), `after`, `limit` ⇒ `{folder (with path) | null, items, next}` |

Library items are ordered folders, then Files, then Documents, each by ID unless `sort` orders inside each kind (never a global recent list; `label` leaves Folders out), and carry `type: "folder" | "file" | "document"`, `id`, `title`, `folderId`, `projectId`, `visibility`, `archived`, `createdAt`, `updatedAt`, `ownerId` plus `labels` and `fileType`/`mediaType`/`byteLength` for Files and `labels` and `editToken` for Documents. `next` is an opaque `<kind>:<cursor>` cursor to pass as `after`. Moving a File is `PATCH /files/:id {folderId}`; a Document moves with `PATCH /documents/:id {folderId, editToken}` (the existing edit token still fences content) and may be created with `folderId`. Every placement is atomic with the rest of the edit.

Rules, all enforced in one serialized workspace transaction (writes already lock the workspace row, so concurrent moves cannot form a cycle): organization is human-only; placement keeps workspace and Project fixed; the destination must exist, be unarchived, and be readable and writable by the actor, who must also be the item's custodian. A `user` Folder holds only its creator's `user` items and Folders, so a shared item can never be hidden or widened by a move, and a private Folder's name and contents are never shown to others (items stay directly reachable by their own rules). Narrowing a Folder to `user` is refused while it holds anything shared or anyone else's, and widening an item inside a `user` Folder is refused. Cycles and depth beyond 8 are refused. Only completely empty Folders archive: any File, Document or sub-Folder (archived or not, visible or not) blocks it, nothing cascades, and restoring needs an unarchived parent. Moves never touch bytes, object keys, request identity, source-Run audience, accepted Run/Skill/share snapshots, and launch no Run. Agents create Files only at the top level.

## Persisted identities

Only scalar names and one scalar discriminator change; accepted bytes are never rewritten:

- Object keys, SHA-256 digests, bytes, IDs, cursors and the stored upload request JSON/identity (title, type, labels, project, visibility, media type, source Run) are untouched, so exact upload retries still match and changed retries still conflict.
- Accepted Run `inputs` and the retained `executionScope` string keep the historical private `artifactId` key for accepted Skill supporting files (the Session binding scope has no File key). New admissions serialize the same key, so a populated Environment still binds after the rename; this was checked with real runtime-produced prompt and script scopes. The Run file getter projects that key to `fileId`.
- Stored Skill supporting references may carry `fileId` (current), `resourceId` (Resource era) or `artifactId` (earliest). The owning Skill projection accepts exactly one and refuses dual identities; new writes store `fileId`.
- Frozen share `selection`/`preview`/`snapshot` JSON written as `artifact`/`artifactType` or `resource`/`resourceType` is projected to `file`/`fileType` on read and never rewritten until an explicit human update, publication or revocation.
- `folderId` columns and the `folders` table are new and nullable, so existing rows stay at the top level with every other byte unchanged; a native push replaces the former `files_size` check (8 MiB) with `files_size_100000000` (proved on a populated database: 8 MiB + 1 and 100,000,000 accepted, 100,000,001 and negative rejected).
- Native pg-boss tables, names and payloads contain no File key and are untouched.

## Transfer

Fresh development uses native `bun db:push`. For a populated pre-rename database, stop Otto, inspect/back up the database and review [rename-files.sql](../scripts/rename-files.sql) separately with `ON_ERROR_STOP`. It belongs after the Artifact → Resource ([rename-resources.sql](../scripts/rename-resources.sql)), Schedules, Skills/Tasks and Chats transfers. It requires quiescent Runs and released leases, renames the `resources` table, its constraints and indexes, the Document/Message attachment columns (and PostgreSQL 18's matching NOT NULL constraint names), and changes only ordinary Task-link `resource` discriminators to `file`. It refuses a repeat, mixed or partial state, leftover `artifact` links, un-renamed Chats and busy Runs atomically. It never runs at startup, no numbered migration exists, and a destructive drop/create push suggestion must not be approved. Native push after the rename reports `changed: true` as it does on a fresh database (known Drizzle Kit constraint churn); the resulting constraint, index and column definitions equal a fresh push and no row changes. The procedure is qualified only on disposable private PostgreSQL with controlled storage, not a live transfer, Garage, provider isolation or billing ([validation](evidence/files-validation.md)).
