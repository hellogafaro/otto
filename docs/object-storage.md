# Object storage (S3) as the source of truth for files

Status: P4a built (the S3 `FileStore` driver, library on S3 with a read-through cache; see "Built: P4a" below). Skills and sources on rows plus S3 bundles are built (S1 and S2, see "S1 as built" and "S2 as built"; owner: "skills and sources must be saved to S3 as well, for a proper source of truth").

## Rule

Anything that is a file or a folder of files is stored in S3-compatible object storage (Garage when self-hosted, any S3 elsewhere). The database holds the metadata and the index; S3 holds the bytes; a local disk copy is a cache that agents read by path. Secrets never go to S3: they stay in the `secrets` table (encrypted with `ENCRYPTION_KEY`) and files only keep a `secretId`.

| What | Metadata (DB) | Bytes (S3) | Local disk |
|---|---|---|---|
| Library items | `library` (built) | `library/<id>` through the `FileStore` | cache (disk driver today) |
| Skills | `skills` (built): id, workspace_id, slug, title, description, hash, created_by, created_at, updated_at | `workspaces/<ws>/skills/<slug>/...` (the whole folder: `SKILL.md`, icon, extras) | `<workspace>/skills/<slug>/` materialized for agents |
| Sources | `sources` (built): id, workspace_id, slug, title, type, auth_status, secret_id, hash, created_by, created_at, updated_at | `workspaces/<ws>/sources/<slug>/...` (config, guide, icon, permissions) | `<workspace>/sources/<slug>/` materialized |
| Chat message files (later) | `chats` (planned) | `workspaces/<ws>/chats/<id>/...` | cache |

## Mechanism (one driver, reused)

1. **S3 `FileStore` driver** (`packages/shared/src/library/file-store`): the interface already exists (put, stage, get, open as a stream, delete, keys are ids). Add an `s3` driver next to `disk`, using Bun's built-in `S3Client` (no dependency; endpoint, bucket, region and keys from env, credentials in Infisical). `OTTO_STORAGE=disk|s3` picks it. Library is the first user.
2. **Bundles** (skills, sources): a folder is a set of keys under one prefix. Writes go DB-row-first (`updatedAt` guard, same two-phase idea as library saves), then S3, then the local copy is refreshed.
3. **Disk is a cache that agents edit.** Agents change `SKILL.md` or a source's config by path. The existing config watcher (it already watches skills and sources) pushes a changed file to S3 and bumps the row's `updatedAt`; the server materializes from S3 at boot and when another node changes a bundle (the `domain:changed` push carries `skills` / `sources`). Conflicts: the newer `updatedAt` wins, a refused push reloads the local copy and toasts.
4. **No S3 configured:** the disk driver stays the default (local desktop, dev), so nothing changes for a single machine.

## Built: P4a

Library bytes can live in S3. Code: `packages/shared/src/library/{file-store,s3-file-store,storage}.ts`.

- **Selection.** The headless server calls `initFileStorage()` at boot (`packages/server/src/index.ts`); the desktop app never does, so it stays on disk. `OTTO_STORAGE=disk|s3` (default `disk`). With `s3`: `OTTO_S3_ENDPOINT`, `OTTO_S3_BUCKET`, `OTTO_S3_REGION`, `OTTO_S3_ACCESS_KEY_ID`, `OTTO_S3_SECRET_ACCESS_KEY` are required (the server refuses to boot naming the missing ones, never the values) and `OTTO_S3_PREFIX` is optional (a folder in the bucket; default none). Path-style addressing (`<endpoint>/<bucket>/<key>`), which Garage and minio need and AWS accepts. The driver is Bun's built-in `S3Client`; credentials are never logged (the boot line shows bucket and endpoint host only).
- **Keys.** `[<prefix>/]workspaces/<workspaceId>/library/<itemId>`: one object per item, no rev in the key. The `rev` prefix of decision 7 is for bundles (skills, sources), where a write is many objects; a library write is one object and S3 overwrites an object atomically, so the item's `updatedAt` guard in the database stays the single commit point.
- **Save.** `stage` keeps the bytes in memory and uploads nothing; `commit` is the one PUT, run after the guarded row update (Bun's S3 has no server-side copy, so the plan's "temp key then copy" was dropped as it adds a request and a leaked-object case for nothing). A failed PUT throws and the library puts the row back; a failed or discarded stage never touches the stored object.
- **`FileStore` interface.** Added `list(prefix?)` (keys relative to the store; disk and S3 alike; for the bundle sync in P4b). Keys stay validated ids.
- **Read-through cache rule.** `<workspace>/library/<id>` stays the path agents read. On S3 it is a cache: valid while the ETag recorded at `<workspace>/library/.etags/<id>` equals the object's current ETag (one HEAD per `get`/`open`). `get`/`open` download a missing or outdated file (streamed to a temp file and renamed, never buffered whole), then serve it from disk; `put` and a committed save write the new bytes through; `delete`, or a read that finds the object gone, drops the cached file. On `disk` the directory is the store and nothing changes.
- **Not wired yet.** Nothing fills the cache before an agent turn that names a file on a node that did not receive the upload (restart with an empty disk, a second node): a read through the library (`library:read`, `get`) does. Calling the store's `get`/`open` before building a turn's attachment paths is the P4b/P3 step. Existing library files are not copied to a bucket when switching from `disk` to `s3` (`list` plus `put` is the migration, not built).
- **Tests.** `packages/shared/src/library/__tests__/`: `s3-double.ts` is a small in-process S3 server (PUT, GET, HEAD, DELETE, ListObjectsV2); `file-store.contract.test.ts` runs one suite against the disk and the S3 driver; `s3-file-store.test.ts` covers the cache, key layout, env and the library domain on S3. Against a real Garage or minio: create a bucket, then run `OTTO_TEST_S3_ENDPOINT=http://localhost:3900 OTTO_TEST_S3_BUCKET=<bucket> OTTO_TEST_S3_REGION=garage OTTO_TEST_S3_ACCESS_KEY_ID=<id> OTTO_TEST_S3_SECRET_ACCESS_KEY=<secret> bun test packages/shared/src/library/__tests__/file-store.contract.test.ts` (it uses a unique prefix and deletes what it wrote). Not run here: no Garage or minio is installed.

## S1 as built: skills on rows plus S3 bundles

Code: `packages/shared/src/skills/{schema,bundle,store,import,storage,index}.ts`, the path keys in `library/{file-store,s3-file-store,storage}.ts`, the skills part of `config/watcher.ts`, `server-core/src/handlers/rpc/skills.ts`.

- **Table.** `skills(id, workspace_id, slug, title, description, hash, created_by, created_at, updated_at)`, unique `(workspace_id, slug)`, explicit snake_case columns. No `scope` (only workspace skills exist) and no `icon` (read from the bundle). `title`/`description` come from SKILL.md's frontmatter (`name`, `description`), parsed in one place (`parseSkillFile`, `skills/storage.ts`) and refreshed on every write; `hash` is the sha256 of the sorted manifest (path, size, sha256 per file).
- **Keys.** Path keys through the same `FileStore`: `[<prefix>/]workspaces/<ws>/skills/<slug>/<path>` (`createDiskFileStore(dir, { paths: true })`, `createS3FileStore({ paths: true })`; `list(prefix)` is the bundle listing; no `..`, no hidden segment). Deviation from data-architecture decision 6: no `rev` prefix and slug, not id, in the key (simplified: the guarded row update is the commit point). On S3 reads go straight to the bucket (no `cacheDir`); on disk the store is `<workspace>/skills` itself, so a bundle is already where agents read it.
- **Write order.** `createSkill`, `updateBundle(workspaceId, slug, files, expectedUpdatedAt)` and `deleteSkill` are row first: the guarded `UPDATE ... WHERE updated_at = expected` is where two writers are told apart (`conflict`), then every file is uploaded and keys no longer in the bundle are deleted; a failed upload puts the row back (or removes a created row). Equal `hash` writes nothing. Limit: a bundle is many objects with no version in the key, so a crash between the row and the last upload leaves a mixed bundle until the next write (the local folder is still there to push again).
- **Folder and bucket stay equal** through `syncLocalSkill(ws, slug)` (watcher, boot and a change from another node all call it; calls for one bundle are serialized). On S3 the folder carries a hidden `.otto-bundle.json {updatedAt, hash}`, the row it was last made equal to. New folder, no row, no marker: becomes a skill (created by the workspace's first owner). Folder hash equals the row: nothing. Folder untouched since the marker but the row moved on: materialized (downloaded to `.tmp-*`, swapped in by rename). Folder edited: pushed with `expectedUpdatedAt` = the marker's; refused means the row is newer, so it wins: the folder is reloaded from it, the losing copy is kept in `<workspace>/.conflicts/skills/<slug>-<ms>/` and the server pushes `skills:conflict` (the app toasts). Folder with a marker and no row: deleted elsewhere, removed. Folder gone: restored from the bucket (S3) or the row dropped (disk). A SKILL.md that does not parse is left alone (`invalid`). On disk there is no marker and no download: the folder always wins.
- **Watcher.** Any non-hidden file change under `skills/<slug>/` is debounced 1 s per bundle and calls `onSkillChange(slug)`; `session-manager` runs `syncLocalSkill`, then pushes `domain:changed` `skills` and `skills:changed` (the same event the app already listened to, now carrying the rows' list). Removing a folder by hand does not delete the skill; `skills:delete` does.
- **Boot.** `initSkills()` (headless `bootstrapServer`, desktop main, `workspaces:create`): `initSkillsImport()` (once per workspace, `imports` setting key `skills:<id>`, logs `imported N skills`; old folders are never deleted; a bad slug or SKILL.md is skipped and counted), then `syncSkills(ws)` for every local workspace, which is the materializer. A bucket that is down is logged and the server still starts. Moving from disk to S3 uploads the bundles the bucket never had on the first sync.
- **RPC.** `skills:get` lists the rows (`getLoadedSkills`: each row read from its folder for the body, icon and frontmatter extras, row-only when the folder is missing); `skills:getFiles`, `openEditor`, `openFinder` only accept a slug that is a row (a client string never becomes a path); `skills:delete` removes row, bundle and folder. Guards (`authorize.ts`): members read; delete needs the skill's creator or a workspace owner. `skills:delete` is in `WRITE_CHANNELS` (`domain:changed` `skills`); the app reloads on it (`useLiveData`). The Skills page lost its Scope filter, tile caption and info row; `?scope=` is ignored.
- **Not built.** No inbound transport exists for a `domain:changed` from another node (one server process per install): `syncSkills(ws)` is what it would call. Sources (S2) reuse `getBundleStore(root, ws, kind)` and the same sync. Resource import/export still reads and writes the folder and notifies the watcher, so it goes through the same sync. Not run against a real Garage or minio.
- **Tests.** `skills/__tests__/store.test.ts` (round trip and two writers on the S3 double, materialize, delete elsewhere, disk driver, disk to S3, importer idempotence, path keys), `skills/__tests__/storage.test.ts`, `server-core/.../skills.isolated.ts` (handlers, path safety, guards matrix, `domain:changed`), the extended `domain-changes.test.ts`.

## S2 as built: sources on rows plus S3 bundles

Code: `packages/shared/src/bundles/{bundle,store}.ts` (the machinery S1 had inside the skills store, now shared), `sources/{schema,store,rows,import,index}.ts`, the sources part of `config/watcher.ts`, `credentials/manager.ts`, `server-core/src/handlers/rpc/{sources,oauth}.ts`.

- **One store for both kinds.** `createBundleStore(db, spec, targetFor)` (`bundles/store.ts`) is S1's write order, `syncLocal`, materializer, conflict copy and queue, moved out of `skills/store.ts`; a kind passes its table, its main file (`SKILL.md`, `config.json`), `index(files)` (the columns the row gets from the bundle) and `toItem`. `createSkillsStore` and `createSourcesStore` are thin wrappers (skills behaviour and tests unchanged). `getBundleStore(root, ws, 'sources')` gives the path-key store; `.conflicts/sources/` holds a refused push's losing copy. Limit: the store is typed against the skills table and the sources table is passed with one cast (the columns only sources has, `type`, `auth_status`, come from `index()`).
- **Table.** `sources(id, workspace_id, slug, title, type, auth_status, secret_id, hash, created_by, created_at, updated_at)`, unique `(workspace_id, slug)`, explicit snake_case columns. `title`, `type` and `auth_status` are read from `config.json` (`name`, `type`; `auth_status` is `error` for `connectionStatus: failed`, `needs_auth` for `connectionStatus: needs_auth` or an auth type that is not `none` without `isAuthenticated`, else `ok`) and refreshed on every write. A `config.json` that does not parse, has no name or a type other than `mcp|api|local`, or a slug outside lowercase letters, digits and hyphens, is `invalid` and left alone.
- **Credentials.** A source keeps one secret (`secret_id`): JSON of the old `StoredCredential` plus its kind (`source_oauth`, `source_bearer`, `source_apikey`, `source_basic`). `CredentialManager.getSourceCredential / setSourceCredential / deleteSourceCredential` take the same `CredentialId` as before (`workspaceId` is now the workspace's id, `sourceId` the slug) and read and write that secret; `SourceCredentialManager` (OAuth tokens and their refresh, bearer tokens, API keys, MCP OAuth) goes through them, so nothing else changed in the OAuth flows. Saving another kind replaces the credential; a write of it touches neither `updated_at` nor the bundle, never goes to S3, and a rolled-back bundle write leaves it alone; `deleteSource` and `deleteWorkspaceCredentials` remove the secret. A credential for a folder that has no row yet syncs the folder first. `loadSource` now sets `LoadedSource.workspaceId` to the workspace's id (`getSourceWorkspaceId`; it was the name of the workspace's folder). The raw `manager.get/set/delete` still address `credentials.enc`, which is only read, by the importer. Deleted as replaced: `CredentialManager.deleteSync` and `ensureInitializedSync`, the backend `deleteSync?` interface member, the folder-only `deleteSource` of `sources/storage.ts`.
- **Importer.** `initSourcesImport()` (once per workspace, `imports` key `sources:<id>`, remote workspaces skipped): `syncSources(ws)` makes rows of the existing folders (created by the workspace's first owner, a bad folder skipped and counted), then every source without a secret gets the credential `credentials.enc` has for it, found under the workspace folder's name (the old key) and the kind `SourceCredentialManager.getCredentialId` picks for its config (an MCP source also tries the other of OAuth and bearer). Old folders and `credentials.enc` are never deleted or changed; the old file is still there until P7.
- **Boot and sync.** `initSources()` next to `initSkills()` (headless `bootstrapServer`, desktop main, `workspaces:create`). The watcher debounces any non-hidden file under `sources/<slug>/` for 1 s and calls `onSourceSync(slug)`; `session-manager` runs `syncLocalSource`, then pushes `domain:changed` `sources`, `sources:changed` (now the rows' list) and, for a folder replaced from the bucket, reloads the chats' source servers (the watcher sees a swap, not an edit). A refused push pushes `sources:conflict` (the app toasts). The watcher and `loadWorkspaceSources` ignore hidden folders (`.tmp-*`, `.old-*`), which the materializer uses.
- **RPC and guards.** `sources:get` lists the rows (`getLoadedSources`: each read from its folder, row-only and switched off when the folder is not there); `sources:create` writes the folder, then the row made by the caller; `sources:delete`, `sources:saveCredentials`, `sources:getPermissions`, `oauth:start` and `oauth:revoke` only accept a slug that is a row (a client string never becomes a path). Guards (`SOURCE_WRITE_CHANNELS` in `authorize.ts`): members read and create; the source's creator or an owner of the workspace deletes it and saves, starts or revokes its credentials. A source made by an agent (`agent:<id>`) or by the first-owner fallback has only owners as writers. `sources:create`, `sources:delete`, `sources:saveCredentials` and `oauth:revoke` are in `WRITE_CHANNELS` (`domain:changed` `sources`); the app reloads on it (`useLiveData('sources')` in `app-shell.tsx`). No page was redesigned. There were no global or project source tiers and no TTL caches in the sources code to delete.
- **OAuth callback.** Unchanged: the server route `/api/oauth/callback` (`http-server.ts`, `completeOAuthFlow`) already exists and the web UI's `performOAuth` uses it as the redirect URL; the desktop app keeps its loopback listener (`callbackPort`), which is not tied to the source store, so moving it to the server route is a separate change and was left.
- **Not built / unverified.** `agent/**` was not changed (it still reads the local copy of a source's folder, which is what the materializer keeps current; its `claude-context.ts` and `session-mcp-server` read and write `config.json` by path, and the watcher syncs those writes). The sign-in flows against real providers, a real Garage or minio, and the watcher's 1 s debounce on a real file system are not run here. The importer was not run against a real `~/.otto`.
- **Tests.** `sources/__tests__/store.test.ts` (round trip on the S3 double, `auth_status`, invalid configs, sync and two writers, delete elsewhere, swap folders, credentials in `secrets` and nowhere else, disk driver, importer idempotence and old files kept), `server-core/.../sources.isolated.ts` (handlers, path safety, the guards matrix with the sign-in channels, `domain:changed`), `skills/__tests__/store.test.ts` unchanged on the shared store.
