# Running the Otto backend

Run from the repository root with Bun 1.4.2. Production values stay in the authorized Infisical project. Link only after the operator supplies the verified Otto project/environment/path, following the secrets skill; do not invent a project or copy another application's credentials. No `.env` file is needed.

Required server fields: `DATABASE_URL`, `BETTER_AUTH_SECRET` (at least 32 characters), `ENCRYPTION_KEY` (canonical base64 encoding of exactly 32 bytes), and `OTTO_ORIGIN` (exact HTTP(S) origin, without a trailing slash/path or credentials). `HOST` defaults to loopback; Compose explicitly uses `0.0.0.0`. `PORT` defaults to 43001. Before MVP, native Drizzle push synchronizes the declarative domain schema for development before startup; there is no numbered app migration chain. The module is `queue.ts` and the schema is `queue`. Official Mastra owns the separate `mastra` schema in the same PostgreSQL database; app schema push must not delete it. A database containing the former `otto_jobs` schema is refused without mutation; migration must not abandon pending jobs. `bun db:push` creates pg-boss's library-owned schema/queues using the pinned library construction SQL, with automatic runtime DDL disabled. An existing incompatible pg-boss schema must use the pinned library's supported upgrade procedure; do not reset it to bypass a startup failure. Concurrent schema bootstrap commands serialize through a PostgreSQL session advisory lock.

Storage fields are all-or-none: `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`; `S3_REGION` defaults to `garage`. Mail fields are all-or-none: `MAIL_FROM`, `RESEND_API_KEY`. Resend credentials should have sending access only, with the sender domain verified in the provider. `TRANSFER_BASE_MS` (default 60000) and `TRANSFER_MIN_BYTES_PER_SECOND` (default 262144) set the file-transfer deadlines: a fixed allowance plus the size at the minimum rate, and a stall limit of the smaller of 30 s and the allowance; the transfer routes disable Bun's own idle timeout in favor of these. `UPLOAD_SPOOL_DIR` (default: the system temporary directory) and `UPLOAD_SPOOL_BYTES` (default 500000000, minimum 100000000, one budget for uploads and download verification together) size the private transfer spool; each server instance owns a 0700 subdirectory, removes only abandoned instance directories whose recorded owner process (PID and kernel start time) is gone, and needs that much free disk. The base must be local to one host and PID namespace; a base shared by containers or hosts with separate PID namespaces is unsupported because ownership cannot be proven across them. The HTTP API endpoint is fixed in production. No credentials, reset/verification links, message content, or raw provider errors belong in logs. The process does not automatically retry an ambiguous email send; user-triggered verification/reset creates a fresh request. An installation without a sender can authenticate existing verified accounts but cannot register new accounts.

Dictation: `OPENROUTER_API_KEY` enables `POST /api/transcriptions` (raw `audio/*` body, 25 MiB cap, authenticated, forwarded and never stored); without it the route answers 501 `not_configured`. `TRANSCRIPTION_MODEL` (default `mistralai/voxtral-mini-transcribe`) is any OpenRouter speech-to-text model. A request is bounded to 20 s, hedged with a second request after 1.5 s and retried once on a transient failure; the first success wins. Failures map to 504 `timeout`, 503 `unavailable` and 502 `failed` without provider bodies.

`GET /health` is liveness and reports unavailable compute honestly. `GET /ready` checks PostgreSQL/queue and configured private storage; it returns 503 while stopping or dependencies fail. `bun scripts/health.ts` exits nonzero on unsuccessful readiness. Readiness does not attest to provider authorization, real inference or outbound mail deliverability. SIGTERM/SIGINT stops admission, closes realtime delivery, drains HTTP, closes queue workers/native runtime/storage, and ends PostgreSQL connections. A second signal does not start overlapping cleanup. The executable exits nonzero after 25 seconds if shutdown cannot finish. Restart retains uncertain Run outcomes rather than blindly replaying tool effects.

## Native provider accounts

Creator-authorized Model settings store API keys using the server-only encrypted Secrets domain. OpenAI Responses, Anthropic and explicitly configured OpenAI-compatible protocols retain the accepted account/model/endpoint identity throughout each Run. Requests use pinned public DNS targets and reject redirects/private addresses. Credential replacement changes account identity and fences old Runs; no key is returned to the UI or model.

The managed gateway, Pi packages and device-login flow are removed. Unsupported old subscription records are not converted or executed. Confined computer provisioning remains deferred; this profile does not itself provide Agent isolation. See [native acceptance](native-acceptance.md) for separate controlled and real-provider evidence.

## Self-host composition

`ops/compose.yaml` is an unqualified single-host deployment example with PostgreSQL, Garage, one Otto server and Caddy/static web. Private database and Garage ports are not published. Only Caddy publishes 80/443. Named data volumes persist across process/container replacement. The native restoration removes its gateway stage but does not build, deploy or certify this composition.

Pinned images: Bun 1.4.2, PostgreSQL 18.4, Garage 2.4.1, Caddy 2.10.2. Garage's [official release index](https://garagehq.deuxfleurs.fr/_releases.html) lists 2.4.1 on 8 September 2026 and its static Linux binary. Its [S3 compatibility reference](https://garagehq.deuxfleurs.fr/documentation/reference-manual/s3-compatibility/) documents path-style requests and private per-key bucket permissions; it does not replace runtime conditional-write qualification. The adapter uses ordinary signed single-part objects and optional checksums only when required. The pinned [PutObject handler](https://git.deuxfleurs.fr/Deuxfleurs/garage/src/tag/v2.4.1/src/api/s3/put.rs) does not inspect `If-None-Match`; its [API dispatch](https://git.deuxfleurs.fr/Deuxfleurs/garage/src/tag/v2.4.1/src/api/s3/api_server.rs) invokes that handler directly. Therefore Otto does not rely on conditional writes for immutable bytes. New keys contain the durable intent UUID and saved SHA-256; the adapter validates the bytes, reconciles an existing key by reading its exact size/digest, and verifies a new write by reading it back. Different bytes cannot pass the digest-key check. Saved legacy keys remain readable; a matching existing legacy object reconciles safely, while an absent legacy pending object fails explicitly and retains its intent for operator recovery. Garage's [configuration reference](https://garagehq.deuxfleurs.fr/documentation/reference-manual/configuration/) supports `GARAGE_RPC_SECRET` from the process environment and persistent metadata/data directories. This profile enables metadata/data fsync and uses one replica; it has no redundancy.

Set non-secret `OTTO_SECRET_ENV` and `OTTO_SECRET_PATH` to the verified scope, then use `ops/run.sh <compose arguments>` only with separate deployment approval. That wrapper invokes the official `infisical run` CLI before Compose. Never run `docker compose config` with injected secrets because interpolation prints values. The scope must supply `POSTGRES_PASSWORD`, a matching managed `DATABASE_URL`, `GARAGE_RPC_SECRET`, server/auth/encryption/storage/mail fields, `OTTO_HOST`, and `OTTO_ORIGIN`.

First setup requires operator authorization to start services. Start PostgreSQL/Garage, assign and apply a single-node Garage layout, create the private bucket, and provision/import its key through the secrets manager using a purpose-built no-output process. Do not use Garage key-generation commands that print secrets to the terminal. Grant only the dedicated bucket to the server key; do not enable website hosting/public access. Then run the one-shot schema bootstrap and start server/Caddy. Garage authorization provisioning remains blocked until a verified credential scope is available; the profile intentionally has no embedded example key or automatic unsafe key bootstrap.

## Backup and restore

Restore PostgreSQL metadata and Garage bytes from one coordinated recovery point. A metadata snapshot alone is not an object backup. Garage documents [metadata recovery and its limits](https://garagehq.deuxfleurs.fr/documentation/operations/recovering/). For this single-node profile use a cold backup: stop Caddy/server and wait for their graceful exits; stop Garage and PostgreSQL cleanly; snapshot/copy all three data volumes together (`postgres`, `garage-meta`, `garage-data`) into an encrypted operator-managed backup. Include the exact application commit, pinned service versions, non-secret Garage configuration, and a manifest with checksums. Keep Infisical credentials/key recovery separately under the verified secrets policy. Do not copy live LMDB/PostgreSQL files or snapshot only one side while writes continue.

Restore into new empty isolated volumes under the same pinned database/Garage releases; never overwrite the live installation. Restore all three volumes and non-secret configuration, inject the original authorized credentials, start PostgreSQL/Garage, and verify layout/bucket permissions before enabling the application. Inspect schema compatibility before any development push; never treat push as a production restore or automatic destructive upgrade. Verify a pre-backup resource through Otto's authenticated download path with its saved size/hash, verify revoked users still fail, and inspect queued/uncertain Runs before allowing further work. Delete no source data or backups as part of verification. Production recovery is not certified until that full rehearsal passes.

This lane cannot execute the cold backup/restore proof because the required Garage credential scope is unavailable. PostgreSQL-only or protocol-fixture checks are not a substitute for coordinated Garage restore.
