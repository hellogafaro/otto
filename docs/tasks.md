# Tasks

`@otto/tasks` owns Tasks, links and manual Timesheets. A Task keeps one authoritative human `ownerId` (human-only Done, owner/reopen/removal gates unchanged); everything below is additive.

## Assignees

A Task has zero or many human and Agent assignees in the pure junctions `tasks_users` and `tasks_agents` (workspace-composite FKs, primary key `(taskId, member)`, member-side index). Public Tasks carry sorted `assigneeUserIds` / `assigneeAgentIds` (at most 20 each). There is no singular alias and no stored array. Create and the one allowlisted `updateTask` accept the arrays: omitted keeps a kind, `[]` clears it, a given array replaces it, all under the Task `editToken`. Writing assignees needs a human actor and Project writer; every user must be a current workspace and Project member who is not a viewer, every Agent must be visible to the actor and unbound or bound to the Task's Project. User IDs are case-sensitive; Agent IDs are canonical UUIDs, so case variants collapse and duplicates reject. Assignment grants no access and starts no Run. Stored assignments stay readable after a member or Agent later becomes ineligible; writing them again requires current eligibility. `getTasks` filters `assigneeUserId` / `assigneeAgentId` mean "contains member" and cannot duplicate rows or pagination.

Populated databases move from the single-assignee columns with the reviewed, private-only [move-task-assignees.sql](../scripts/move-task-assignees.sql) (stop Otto, back up, run with `ON_ERROR_STOP` before `bun db:push`); fresh databases use `bun db:push`. It refuses a repeat and never runs at startup.

## Due date and recurrence

`dueAt` is an ordinary nullable date. `recurrence` is one nullable RFC 5545 text value, `DTSTART;TZID=<IANA zone>:<local time>` and one `RRULE:` line (at most 400 bytes). The server validates it strictly and re-serializes it. Supported: `FREQ` DAILY/WEEKLY/MONTHLY/YEARLY, `INTERVAL` (1000 at most), `BYMONTH`, `BYMONTHDAY`, `BYDAY` (ordinals only for MONTHLY/YEARLY; YEARLY ordinals stop at +/-52, and without `BYMONTH` a YEARLY `BYDAY` cannot mix ordinal and plain weekdays or sit beside `BYMONTHDAY` with an ordinal, because the library spills 53 into the next year, silently drops the plain weekdays and ignores `BYMONTHDAY`; MONTHLY forms, YEARLY forms with `BYMONTH`, and plain-weekday plus `BYMONTHDAY` are supported. A randomized comparison with an independent calendar oracle over about 10,000 rules, run without skipping any combination, found no other mismatch), `BYSETPOS`, `WKST`, and `COUNT` (1000 at most) or `UNTIL` (UTC, as RFC 5545 requires with a TZID), not both. Rejected: sub-daily rules, `BYHOUR/BYMINUTE/BYSECOND/BYWEEKNO/BYYEARDAY`, `RSCALE`, `RDATE/EXDATE/EXRULE`, unknown parts, extra lines, floating or UTC `DTSTART`. Part names are case-insensitive and a repeated part in any case is rejected. Evaluation is bounded (the library's candidate-evaluation budget is lowered from its default of 1,000,000 to 10,000; this bounds work, not wall time. In measured examples a rule that took about 3.5 s of synchronous work now fails in tens of milliseconds, and an independent sweep of about 9,000 rules peaked at 218 ms for one parse) and every instant must be at most year 9999. A rule is rejected when written if it has no occurrence, cannot be evaluated within the budget now (and, for COUNT, when walked to its end), or produces an instant beyond year 9999. Legitimate sparse (Feb 29 on a Monday, COUNT=100), leap, INTERVAL=1000 and COUNT=1000 rules were measured to pass; a rule that genuinely needs more work is rejected with an explicit limit error rather than accepted. A stored rule that later hits a limit, goes beyond year 9999 or finds no occurrence without COUNT/UNTIL makes Done a conflict before any write; only a COUNT/UNTIL rule with no occurrence left is treated as exhausted. There is no series table, queue or sweep.

When an authorized human moves a Task to Done and it has a rule, the same transaction creates one successor: a `todo` Task due at the first occurrence strictly after the server completion instant (Sunday completion with a Monday rule gives tomorrow; Tuesday gives next Monday; completion exactly on an occurrence gives the next one). It copies title, notes, owner, project and the original `recurrence` text, so the DTSTART anchor, INTERVAL phase, COUNT and UNTIL never restart. Eligible assignees are copied; ineligible ones are dropped and the completed Task keeps its own. An exhausted rule completes without a successor; archived Tasks create none. The owner must still be an eligible Project member, otherwise Done is rejected and nothing changes. A stored rule that can no longer be evaluated is also a conflict before any write.

`tasks.predecessorId` (server-only, `UNIQUE`) is the one-successor fence; public Tasks also show the derived `successorId`. Reopening and completing again, a repeated Done, or concurrent completion find the existing successor and create no second one (the stale `editToken` loser gets a conflict). The completed Task and its Timesheets are never copied or changed.

## Parser qualification

`rrule-temporal` 2.2.8 (MIT, already in the lockfile through pg-boss) was qualified on Bun 1.4.2 (native `Temporal`) in a scratch directory: results were identical under three host `TZ` values, ignore nonexistent local times without counting them (RFC 5545 §3.3.10), pick the earlier repeated instance, keep month-end and leap rules correct, and fail large or empty rules through an iteration cap instead of hanging. It accepts unknown parts, extra rules, EXDATE and floating start times, so Otto validates first. `rrule` 2.8.1 was rejected: its results depended on the host time zone and it included the nonexistent local time. These probes cover the exercised rules only.
