# Users and workspaces (plan)

Status: phase 1 backend built (see "Phase 1 as built" below) and private chats built ("Phase 3 as built"); the rest is proposal. Evidence is cited as `file:line` (line numbers in the older sections predate the build); `v1:` means `git show otto-v1-archive:<path>`. Better Auth facts are from its docs as of 2026-10-06 (`better-auth` 1.7.7, pinned).

## Phase 1 as built (backend)

- **Code.** `packages/shared/src/users/{schema,index}.ts` (Better Auth tables, `createUsersStore(db, options)` / `initUsersStore()`, `initAuth()`, the sign-up gate, `initOwner`, `initLocalUser`, `initFirstOwner`), `workspaces/{schema,members}.ts` (organization tables `workspaces`, `workspaces_members`, `workspaces_invitations`; `updateWorkspaceMirror`, `initWorkspaceOwner`, `hasPendingInvitation`), `updateLegacyUserActor(db, actor)` in `library`, `projects` and `tasks`, `actors.ts` (`userActor`, `isActor` accepts `user:<12 chars>` and `agent:<id>`), `config/storage.ts` (`refreshWorkspaceMirror` after add, discovery, remove; the rename handler in `handlers/rpc/settings.ts`), `packages/server-core/src/bootstrap/identity.ts` (WebSocket identity), `webui/http-server.ts` (Better Auth at `/api/auth/*`, `GET /api/setup`).
- **Env.** `BETTER_AUTH_SECRET` (required, at least 32 characters, separate from `ENCRYPTION_KEY`; the server and `initUsersStore()` refuse to start without it), `BETTER_AUTH_URL` (the public origin; https makes cookies Secure), `BETTER_AUTH_TRUSTED_ORIGINS` (comma-separated extra origins for `/api/auth`, e.g. `http://localhost:5175,http://localhost:9100` in dev), `OTTO_SERVER_TOKEN` (machine, CLI and WebSocket credential, acts as the first user; not a sign-up credential), `OTTO_OWNER_EMAIL` (optional: the only email that may make the first account), `OTTO_WEBUI_SECURE_COOKIE` (optional true/false override), `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` and `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET` (each pair switches that provider on). `OTTO_WEBUI_PASSWORD`, the jose JWT, the per-IP limiter, `POST /api/auth` and `login.html` are gone. Dev values are in Infisical (project `otto`, env `dev`).
- **First owner.** Open `/login` on a fresh install, it asks `GET /api/setup` and shows "Create the owner account" (name, email, password, no token). The first sign-up (`POST /api/auth/sign-up/email`) becomes owner of every workspace and inherits every legacy `'user'` row. With `OTTO_OWNER_EMAIL` set only that email (trimmed, case-insensitive) may make it: any other gets `403 OWNER_ONLY`. Without it the first sign-up wins, and while no user exists the server logs one warning at boot (`The first sign-up will own this server; set OTTO_OWNER_EMAIL to restrict it`), nothing once an owner exists. Later sign-ups need a pending, unexpired invitation for exactly that email: `403 INVITATION_REQUIRED`. The first-sign-up check and its claim run without an await in between, and a concurrent test with a slowed insert proves exactly one wins.
- **First-run setup.** A fresh server has no workspace, so the first owner lands on "Name your workspace" (`server:createWorkspace`: a folder under `CONFIG_DIR/workspaces`, owner membership and mirror row), then, as an owner while no AI connection is usable and nobody skipped, on "Connect an AI provider" ("Skip for now" sets the install-wide `setupDeferred`). Invited members skip both (`getFirstRunStep` in `apps/electron/src/renderer/components/first-run/`; DESIGN.md, First-run setup).
- **Identity.** The WebSocket handshake resolves a user: session cookie or bearer token (Better Auth's bearer plugin; the sign-in response carries it in `set-auth-token`) is that session's user; the server token (and the desktop app's per-launch token) is the first user (earliest `createdAt`), refused while no user exists. `RequestContext.userId` carries it; a reconnect must come from the same user. Handlers for library, projects, tasks and chat attachments take the actor from `ctx.userId` (`actorOf(ctx)`); the domains no longer default `createdBy`. The desktop app makes its local user at launch (`initLocalUser`, name and email from `preferences.json`, else `You` / `local@localhost`).
- **Where the plan was corrected.** Invitation rows are not deleted on accept or revoke: the plugin keeps them with `status` `accepted`, `rejected` or `canceled`, and the gate only counts `pending` ones. The plugin's `organization` table also has `logo` and `metadata` (and no `updatedAt`); the mirror leaves them empty. The organization plugin's own create, update and delete endpoints are disabled (`disabledPaths`), because workspaces come from the registry and a rename or removal there would drift from it. `beforeCreateOrganization` is not needed: the mirror is written with Drizzle, with our ids, never through the plugin. `better-auth` bundles its Drizzle adapter (`better-auth/adapters/drizzle`), there is no separate package to install. Roles are checked against an allow-list (`owner`, `member`), not only against `admin`.
- **Known limits.** Rate limiting keys on the client address from `x-forwarded-for`; with no such header (a direct connection) every client shares one bucket per path, so sign-in is limited to 3 per 10 s for everyone together, and behind the proxy `advanced.ipAddress.trustedProxies` is still to be set. A sign-out does not close an open WebSocket (the session is checked at connect, as before). Sessions are not re-checked per RPC. The server needs `bun run db:push` before it starts (boot touches the new tables).


## Phase 3 as built (private chats)

- **Rule.** A chat belongs to the user who created it: the session header has `createdBy` (`user:<id>`, in `SESSION_PERSISTENT_FIELDS`), written by the server from `ctx.userId` (`actorOf(ctx)` in `sessions:create`, the importer for `sessions:import` and `importRemoteTransfer`; a bundle's own `createdBy` is ignored). Nobody else sees or touches it, owners included. A chat with no `createdBy` (made before this) belongs to the workspace owners (`getWorkspaceOwnerIds` in `workspaces/ownership.ts`); no data was rewritten. Chats made by the server itself (scheduled automations, the messaging gateway) belong to the workspace's first owner; a test run of an automation to the caller; a spawned subtask to its parent's creator (a legacy parent gives a legacy child).
- **Code.** `server-core/src/sessions/private-chats.ts` (`getChatAudience`, `assertOwnsSession`, `chatNotFound`), `SessionManager` (`canSeeSession`, `setWorkspaceOwners`, a `viewerId` argument on `getSessions`, `getUnreadSummary`, `getActiveSessionsInfo`, `markAllSessionsRead`, `getTaskOutput`), `handlers/rpc/session-guard.ts`. `bootstrapServer` wires the owner lookup into the manager; until it is set, a chat without creator is visible to nobody.
- **Session-id channels: 22, enforced in one place.** `SESSION_ID_CHANNELS` lists them (sessions: getMessages, delete, sendMessage, cancel, respondToPermission, respondToCredential, command, getPendingPlanExecution, getPermissionModeState, getFiles, watchFiles, getNotes, setNotes, export, exportRemoteTransfer; session:getModel, setModel; drafts get, set, delete; messaging generateCode, unbind). `registerCoreRpcHandlers` wraps `server.handle` (`guardSessionChannels`), so each runs `assertOwnsSession` first and answers `not_found` for a chat that is not the caller's, that does not exist, or a missing id (the same answer, so existence does not leak). Channels that filter on their own: `sessions:get`, `getUnreadSummary`, `markAllRead`, `searchContent` (ripgrep hits kept only for visible chats), `server:getActiveSessions`, `drafts:getAll`, `messaging:getBindings`, and `oauth:start` (checks its optional `sessionId`). `session-guard.test.ts` registers every core channel and fails when a handler whose first argument is `sessionId` is not declared, when a declared one is not registered, or when another user (or no user) gets anything but `not_found`.
- **Pushes.** `PushTarget` `all` and `workspace` take an optional `userIds`; `WsRpcServer.matchesTarget` drops other connections (one line). `SessionManager.sendEvent` is the only sender of session events and sets `userIds` to the chat's audience (the creator, or the owners; a chat already gone, e.g. `session_deleted`, passes the audience it had; an unknown chat reaches nobody). The unread summary is pushed per user with that user's count (a user who just lost a chat gets one more push).
- **Agents.** An agent acts for the user its chat belongs to: the session tools that name another chat (`get_session_info`, `list_sessions`, labels, status, archive, background tasks, `send_agent_message`) only reach chats with the same `createdBy`.
- **Known limits.** The files are not private: a chat's folder sits in the workspace and any member's agent or file RPC that reads a path under the home directory can read it (`file:readAttachment`, shell tools); the privacy is at the RPC, list and push level. The messaging gateway (Telegram, WhatsApp) is not tied to a user: its `/sessions` listing and binding act with the workspace as a whole, and its chats belong to the first owner. `server:getStatus` still reports the count of running chats per workspace. Desktop-only IPC (`session:transferToWorkspace`, browser panes, notifications) is single-user and unguarded. An owner removed from a workspace stops seeing legacy chats at once (the lookup is not cached).

## Phase 2 as built (guard, members, assignees)

- **The guard.** `packages/server-core/src/bootstrap/authorize.ts` exports `authorize(ctx, channel?, args?)`; `WsRpcServer` takes it as its `authorize` option (set in `bootstrapServer`, so the desktop app and the headless server share it) and calls it twice: at the handshake without a channel, and before every handler with its channel and arguments. It throws `domainError('forbidden', ...)` (wire code `forbidden`; there is no uppercase transport code for it). Rules: the caller must be signed in; when the connection names a workspace the caller must be a member of it (membership is one Drizzle select per request, so a removal takes effect on the next request); for the channels in `WORKSPACE_ARG_CHANNELS` (a map channel to the index of the argument that names a workspace, 62 entries; `automations:test` carries it as `{ workspaceId }`) the caller must also be a member of that workspace. A workspace reference is resolved with `getWorkspaceByNameOrId`, exactly as the handlers do, so a workspace cannot be reached by its name instead of its id. `OWNER_CHANNELS` (minimal): `workspaces:getInvitations`, `invite`, `removeMember`, `updateMemberRole`, `workspaceSettings:update`, `workspaces:updateRemote`; `workspaces:revokeInvitation` takes an invitation id and checks owner in its handler (`assertOwner`). Handlers stay unaware of users.
- **Handshake and pushes.** A connection whose handshake `workspaceId` is not a workspace of the user is refused (error `forbidden`, close 4403), also on reconnect. `window:switchWorkspace` is in the map, so it is guarded. Pushes were already per workspace (`client.workspaceId`); a user who leaves or is removed has their connections detached (`removeUserFromWorkspace`, workspace set to none), so they stop receiving that workspace's events without being disconnected and can still list and switch. `GET /api/config/workspaces` returns a workspace of the signed-in user.
- **Listing and creating.** `workspaces:get`, `server:getWorkspaces`, `server:getStatus` and `server:getActiveSessions` return only the caller's workspaces. `workspaces:create` and `server:createWorkspace` work for any signed-in user, who becomes `owner`; on a server without a window manager (headless) `workspaces:create` only accepts folders under `CONFIG_DIR/workspaces`; naming the folder of an existing workspace needs its owner (otherwise a creator could take it over).
- **Members.** Plain Drizzle functions in `workspaces/members.ts` over the plugin's own rows (the plugin API needs a session; the local app and the server token have none): `getMemberRole`, `isWorkspaceMember`, `getMemberWorkspaceIds`, `getWorkspaceMembers`, `createWorkspaceMember`, `createWorkspaceInvitation` (lowercase email, role `member`, 7 days, cancels an earlier pending invitation of that email), `getWorkspaceInvitations` (pending and unexpired), `updateInvitationCanceled`, `deleteWorkspaceMember` (removal and leave; the last owner cannot go; cancels the invitations that member sent), `updateWorkspaceMemberRole` (owner or member; the last owner cannot be demoted); each change is one transaction. Failures: `not_found`, `invalid`, `conflict`, `forbidden`. Acceptance stays the plugin's `POST /api/auth/organization/accept-invitation`, used by the login page (the invitation rows are plugin-compatible: tested, including the email binding and expiry).
- **RPCs** (`handlers/rpc/workspaces-members.ts`, REMOTE_ELIGIBLE, positional arguments): `workspaces:getMembers(workspaceId)` returns `[{ actor, userId, name, email, role }]` (any member; the caller's own entry also has `me: true`, how the desktop app's local user, which has no session, knows which member it is); `getInvitations(workspaceId)`, `invite(workspaceId, email)` returning `{ id, email, expiresAt, link }` with `link` = `${BETTER_AUTH_URL}/login?invite=<id>&email=<encoded>`, `removeMember(workspaceId, userId)`, `updateMemberRole(workspaceId, userId, role)` (owners); `revokeInvitation(id)` (owner of the invitation's workspace); `leave(workspaceId)` (any member). Renderer API: `getWorkspaceMembers`, `getWorkspaceInvitations`, `inviteWorkspaceMember`, `revokeWorkspaceInvitation`, `removeWorkspaceMember`, `updateWorkspaceMemberRole`, `leaveWorkspace`.
- **Assignees.** The tasks and projects handlers call `assertWorkspaceActors` (`handlers/rpc/library.ts`): a `user:<id>` in `assignees` or a project member must be a member of the workspace (`invalid` otherwise); `agent:<id>` is not checked.
- **Tests.** `apps/electron/src/main/handlers/__tests__/authorize.isolated.ts` registers every handler (core and GUI) and checks (a) every handler with a workspace parameter is in `WORKSPACE_ARG_CHANNELS` at the right index (read from the handler's parameter names, so a new channel taking a `workspaceId` fails the test until it is declared), (b) over a real `WsRpcServer` with a spy on every channel: another workspace by id, by name or unknown is `forbidden` and the handler does not run, a member is refused on exactly the owner channels, a removed member is refused on every channel, handshakes are refused, `workspaces:get` filtering and `workspaces:create`. `packages/server-core/src/handlers/rpc/workspaces-members.isolated.ts` covers the RPC rules and that a removed member's requests are refused and pushes stop; `workspaces/members.test.ts` the domain rules; `users/users.test.ts` invite, accept through the plugin endpoint, member (and expired, wrong email); `projects-tasks.isolated.ts` the assignee validation.
- **Private paths (closed after phase 2).** The file channels used to allow all of the home directory, so any member could read `~/.otto/config.json` (server and remote tokens in plaintext), `credentials.enc`, `otto.db` (every user's data and the encrypted secrets), other workspaces and other members' chats. One rule in `handlers/utils.ts` now applies to every client-driven path, whatever the allow-list says: `createPathGuard(caller)` returns a function that refuses (a) in `CONFIG_DIR` everything except `config-defaults.json`, `preferences.json`, `window-state.json`, `theme.json`, `themes/`, `tool-icons/`, `docs/`, `permissions/`, `provider-domains.json` and `workspaces/` (so `config.json` and its backups, `credentials.enc`, `otto.db`, `-wal`, `-shm` and backups, `.server.lock`, `drafts.json`, `logs/` are refused to everyone, owners and the local user included; a default-deny list, so a new file there is private until listed), (b) any path inside a registered workspace root of which the caller is not a member (`isWorkspaceMember`), and a folder under `CONFIG_DIR/workspaces` that no workspace claims, (c) `<workspace>/sessions` and `sessions/<id>/` unless `canSeeSession(id, userId)` (private chats). Paths are normalized, `~` expanded and symlinks resolved (`realpath`) before the check. `validateFilePath(path, dirs, caller)` = allow-list + that rule; `assertPathNotPrivate(path, caller)` = the rule alone, for channels that take any path (a folder picker, a draft attachment from anywhere on the user's disk, `git:getBranch`); `callerOf(ctx, deps)` builds the caller. Covered: `file:read`, `readBinary`, `readDataUrl`, `readPreviewDataUrl`, `readAttachment`, `readUserAttachment`, `fs:search` (base path, and every result and subfolder), `fs:listDirectory` (the path and each entry), `shell:openFile`, `shell:showInFolder` (server and Electron copies), `git:getBranch` (server and Electron copies). The server's own callers (agent attachments in `session-manager`, browser uploads) pass no caller and get only the sensitive-file rule. Tests: `handlers/rpc/files-private.isolated.ts` (a table of denied paths over every channel, the allowed ones, `..`, a symlink, `~`), `apps/electron/src/main/handlers/__tests__/system-private-paths.isolated.ts`, `handlers/__tests__/validate-file-path.test.ts`.
- **Known limits.** Not closed by the private-paths change and still open to any member: shell and command execution by agents (an agent runs as the server user and can read anything that user can). (The `llm-connections` and OAuth channels and `settings` writes were open too and are closed since P1c and P1a.). Also: the `workspaces:create` path rule applies only to a server without a window manager (an Electron host in server mode still lets a remote token holder pick a path); a removed member's tasks, project memberships and chats stay; `workspaces:get` and the other per-workspace list calls read the config on every request (the guard resolves the reference with `getWorkspaceByNameOrId`, which reads it); the private-path rule reads the workspace registry on every file call, compares case-insensitively only on macOS and Windows, and does not guard a path created or swapped for a symlink between the check and the read.

## Settings as built (P1a)

- **Who may touch which settings** (`settings(entity, key, value)`, `docs/data-architecture.md` (c)), decided in `bootstrap/authorize.ts` for the generic channels `settings:getSetting(entity, key)` and `settings:updateSetting(entity, key, value)`: `user:<id>` only by that user, to read and to write (the instance owner included); `workspace:<id>` read by its members, written by its owners; `install` written only by the instance owner, read by any signed-in user except the keys marked `sensitive` in the catalogue (`server`, which holds the token), which the instance owner alone reads. An entity that is not one, or a key of another kind of owner, is `invalid`.
- **AI connections (P1c).** Every person connects their own subscription or key and it powers their own agents: a connection has a scope, `user:<id>` (seen and managed by that person only, the instance owner included; their chats resolve it first), `workspace:<id>` (managed by that workspace's owners, used by its members) or `install` (the imported ones; managed by the instance owner, the fallback every chat has). A new connection is the caller's own unless its setup asks for `scope: 'workspace'` or `'install'`. `bootstrap/authorize.ts` `CONNECTION_WRITE_CHANNELS` lists the channels that change one or its credential (setup, save, delete, test, model refresh, default, the Claude, ChatGPT and Copilot sign-in and sign-out, the masked key) and decides by the scope of the connection the argument names; reads (`llm-connections:list`, `get`, the sign-in status) are open to any member and return only what that member may see, never a secret. `docs/data-architecture.md` has the as-built.
- **Instance owner** = the first user (earliest account), who is owner of every workspace in a single-workspace install and who `OTTO_SERVER_TOKEN` and the desktop app act as. `INSTANCE_OWNER_CHANNELS` lists the specific channels that write an `install` setting (default thinking level, keep awake, dismissed update, decision layer, Git Bash path, "Setup later", default connection, server config and status); a workspace owner who is not the instance owner is refused there. This closes "members writing install-wide settings" of the known limits above.
- **Per-user preferences.** The UI preferences and the profile (`colorTheme`, `sendMessageKey`, `timezone`, `notes`, ...) are `user:<id>` settings, so members no longer share them; the existing channels (`input:*`, `theme:*`, `notification:*`, `preferences:read`/`write`) act on `ctx.userId`. Chats and agents use the chat's user (`createdBy`), and the first user where none is known (a chat made before chats were private).
- **Labels, statuses and permission rules (P3a).** They are workspace data in the database, read by every member and written by the workspace's owners: every label and status write channel (`labels:create|update|move|reorder|delete`, `statuses:create|update|delete|reorder|setDefault`) is an `OWNER_CHANNELS` entry, and agents reach them through the `otto` CLI (PT) and the rules through the `permissions_edit` tool, as the chat's user under the same rule (a member's agent can list and get, not change). The workspace rules are the `permissions` setting of `workspace:<id>` (owners write it like any workspace setting); a source's `permissions.json` stays in its folder.

## Owner direction (2026-10-06, supersedes the sections below where they differ)

- **MVP sign-in: email and password, no mail.** Better Auth `emailAndPassword` (`minPasswordLength: 12`, `requireEmailVerification` off, `rateLimit` on). No mail sender, no SMTP, no email verification and no password reset yet (a forgotten password is reset by the operator with the CLI and `OTTO_SERVER_TOKEN`). Google and GitHub are configured but enabled only when their client id and secret env vars are set (off for now). **Later, additively:** a `sendEmail` function (nodemailer over `SMTP_URL`, or Resend) switches on email codes (`emailOTP`), verification, reset and invitation emails without touching the model.
- **Better Auth's organization plugin** (not our own member tables) for workspaces, members and invitations (links for now, mail later). The plugin's `organization` table is a thin mirror of the config workspace registry: `id` = workspace id (`beforeCreateOrganization` returns `{ data: { id } }`, inserted with `forceAllowId`), `slug` = the id too (our route slug is the folder name and is not unique). Mirror writes on `addWorkspace`, `syncWorkspaces`, a bootstrap backfill, removal (cascade) and rename. Tables are renamed with `modelName`: `workspaces`, `workspaces_members`, `workspaces_invitations` (`organizationId` mapped to `workspaceId`, `name` to `title`), declared in `workspaces/schema.ts`.
- **Roles: `owner` and `member`.** The plugin always accepts `admin`; `beforeCreateInvitation` and `beforeUpdateMemberRole` refuse it. Settings: `requireEmailVerificationOnInvitation: false` (no mail yet), `invitationExpiresIn` 7 days, `cancelPendingInvitationsOnReInvite: true`, `sendInvitationEmail` a no-op. **Invitations are links:** the owner enters the invitee email in Settings → Members and copies `/login?invite=<id>&email=<email>`; the invitation row (id = token) is deleted on accept or revoke.
- **Chats are private** to their creator (`createdBy` = `user:<id>` in the session header; even owners do not see others' chats). Everything else in a workspace (projects, tasks, library) is shared by its members.
- **Tasks** use members: the assignee picker lists workspace members, the server refuses a non-member assignee; `createdBy` and `assignees` hold `user:<id>`. Agents later (`agent:<id>` is already a valid actor).
- **Settings → Members** (owners): members, role, remove, leave (last owner cannot leave), invite by email, pending invitations with revoke. Our UI over RPCs that call `auth.api.*` with the caller's bearer token and an explicit `organizationId`. Server mode only (a local Electron install has no Better Auth session).
- **Login** is a React route at the router root (like the 404 page), not static HTML: `design/ui` Input/Button, i18n, theme, the same patterns as today's password page. Modes on one route: sign in (email, password), "Create the owner account" (first run only: name, email, password), and `?invite=<id>&email=<email>` (name and password for the invited email, then the invitation is accepted). `login.html`, `OTTO_WEBUI_PASSWORD` and the JWT are deleted in phase 1.
- **Sign-up gate (updated 2026-10-06: no setup token).** The first sign-up creates the owner, SaaS style: if `OTTO_OWNER_EMAIL` is set only that email may make it (`OWNER_ONLY` otherwise), if not the first sign-up wins and the server logs one warning at boot while no user exists. Every later sign-up needs a pending invitation for exactly that email (checked in `databaseHooks.user.create.before`: throw an `APIError`; returning false crashes the route). An invitation link is a secret: whoever holds it can register that email, so it expires in 7 days and dies on first use. `OTTO_SERVER_TOKEN` is only the CLI, machine and WebSocket credential (it acts as the first user) and is not read by sign-up.
- **No instance `admin` flag** for now.
- Sign-in sets a session cookie; the Electron remote client uses the bearer plugin (`Authorization: Bearer`).
- **Guard.** Membership is one Drizzle select on `workspaces_members`; the transport wrapper uses it. Plugin operations are not transactional: two owners leaving at once can race (accepted).

### Lean plan

1. **Sign-in and identity.** `users` domain (users, `users_sessions`, `users_accounts`, `users_verifications` kept for later mail), Better Auth mounted at `/api/auth/*`, `emailAndPassword`, the sign-up gate, the React login route, identity on the WebSocket (`ctx.userId`), bootstrap (workspace mirror rows, `owner` membership, `'user'` rewritten to `user:<id>`). First test proves Better Auth and the organization plugin on `bun:sqlite` (including our workspace ids as organization ids).
2. **Guard and private chats.** The wrapper around `server.handle` (member of the connection's and any explicit `workspaceId`; `OWNER_CHANNELS`), filtered `workspaces:get`, guarded switch/create; session header `createdBy`, chat list filtered, one `assertOwnsSession` for session-id channels (count them first), old chats to the first owner. One table-driven test over every registered channel.
3. **Members and tasks.** RPC wrappers for the plugin (invite, cancel, accept, remove, role, leave, list), Settings → Members page (Opus), assignee pickers from members, server validation.

Later: mail (codes, verification, reset, invitation emails), remote desktop sign-in UI, agents as actors, API keys, Google and GitHub switched on, a `workspaces` registry moved from the config into the table.

## (a) Recommendation

Better Auth for identity only (email and password, sessions, bearer tokens), stored through the Drizzle SQLite adapter in a new `users` domain. Workspaces stay what they are today (a directory registered in the config, `packages/shared/src/config/storage.ts:613`) and gain one membership table, `workspaces_members`, plus `workspaces_invitations`, owned by the existing `workspaces` domain; we do not adopt the organization plugin. Every connection resolves to one user at the WebSocket handshake, and one guard in the transport checks membership before any handler runs. Two roles: `owner` and `member`. The first user becomes owner of every existing workspace and inherits every legacy `'user'` row. The desktop app in local mode never shows a login: its per-launch token maps to a local user.

## (b) From v1: reuse vs. drop

Reuse:
- Better Auth for humans only, membership as a separate check (`v1:apps/server/src/auth.ts:12`). Config to keep: `emailAndPassword` with `minPasswordLength: 12`, `revokeSessionsOnPasswordReset`, `rateLimit: { enabled: true }`, `trustedOrigins: [origin]` (`v1:apps/server/src/auth.ts:20-94`).
- One authentication entry for every request, and identity never comes from a client field (`v1:apps/server/src/api.ts:34-59`, `v1:apps/server/src/http.ts:50`). The WebSocket rechecks the session on connect (`v1:apps/server/src/realtime.ts:35-46`).
- Membership as `(workspaceId, userId, role)` with a composite primary key (`v1:packages/workspaces/src/schema.ts:63-81`). Invitations bound to an email, 7-day expiry, accepted only by the matching account, revoked when the member is removed (`v1:packages/workspaces/src/index.ts:165-229,254-285`).
- Agents never authenticate: their identity comes from the server-side run (`v1:docs/backend.md:9`).

Drop:
- `installation_setups` and an operator-only CLI claim (`v1:packages/workspaces/src/schema.ts:82-89`, `v1:scripts/bootstrap.ts`): replaced by a first sign-up gated by `OTTO_OWNER_EMAIL` when set (f; it was the server token until 2026-10-06).
- Four roles (`owner/admin/contributor/viewer`, `v1:packages/workspaces/src/schema.ts:72`), owner-vs-admin rules in every mutation (`v1:packages/workspaces/src/index.ts:169-171,371-375`), `requireHuman/requireWriter/requireAdmin` sprinkled per function (`:64-74`).
- The per-transaction row lock and membership check inside every domain call (`inWorkspace`, `:29-63`); a workspace `cursor` (`:286-306`); audience caps; sorted, paginated member directories (`:321-362`).
- Agent sponsors, grants, per-user `visibility` on agents, documents and files (`v1:packages/agents/src/schema.ts:30-32`, `v1:docs/backend.md:23-29`), and project membership enforced on every read (`v1:packages/projects/src/index.ts:111-132`, `v1:apps/web/src/lib/project-membership.ts`). This is what made v1 heavy: the authorization tests (`v1:tests/authorization.test.ts`, `v1:tests/execution-authority.test.ts`) cover sponsor inheritance and grant regrants, not the basics.
- The v1 Members page asked users to paste invitation ids (`v1:docs/evidence/ui-settings-members-desktop-light.png`). We use a link.
- Email verification and mail delivery (v1 required mail in production, `v1:apps/server/src/auth.ts:38-39`). Otto has no mail sender; invitations are copyable links.

## (c) Data model

Better Auth's tables, in `packages/shared/src/users/schema.ts` (the `users` domain owns them; table names are mapped with `modelName`, so plugins and queries keep working):

- `users(id, name, email, emailVerified, image, createdAt, updatedAt)`. Better Auth needs `name`; it is a person's name, not an item label, so it stays `name` (record as an exception beside `library`).
- `users_sessions(id, userId, token, expiresAt, ipAddress, userAgent, createdAt, updatedAt)`. Not `sessions`: that word is a chat in this codebase.
- `users_accounts(id, userId, accountId, providerId, password, accessToken, refreshToken, idToken, accessTokenExpiresAt, refreshTokenExpiresAt, scope, createdAt, updatedAt)`
- `users_verifications(id, identifier, value, expiresAt, createdAt, updatedAt)`
- One extra column, `users.admin` (boolean, default false, via `user.additionalFields`, `input: false`): may change instance settings (server, providers, creating workspaces). The first user is admin.

Ours, in `packages/shared/src/workspaces/schema.ts`:

- `workspaces_members(workspaceId, userId, role, createdAt)`, primary key (`workspaceId`, `userId`); `role` is `owner` or `member`.
- `workspaces_invitations(id, workspaceId, email, role, createdBy, expiresAt, acceptedAt, revokedAt, createdAt)`. `id` is `createId()` and is the link token: it is only accepted by a signed-in user whose email matches (as v1), so a leaked link alone grants nothing.

No `workspaces` table yet. The registry stays the config (`id`, `rootPath`, name in the workspace folder config, `storage.ts:613-643`); `workspaceId` columns in `library`, `projects`, `tasks`, `timesheets` keep pointing at those ids. New workspaces get `createId()` (`generateWorkspaceId`, `storage.ts:596`, is a uuid-like string today); existing ids stay valid. A table comes when the registry must leave the file (hosted, Postgres).

Ids: `advanced.database.generateId: () => createId()`; Better Auth applies it to core and plugin tables. Session tokens are separate random values, not ids.

How the tables are made: run `bunx auth generate --adapter drizzle --dialect sqlite` once, paste the result into `users/schema.ts` with our names (`modelName` per model; Drizzle property names stay Better Auth's field names), and from then on `db:push` owns it like every other `schema.ts`. Never `auth migrate` (Kysely only). Better Auth 1.7's startup `validateSchema` (on outside production) catches drift after an upgrade. Adapter: `drizzleAdapter` from `@better-auth/drizzle-adapter`, `provider: 'sqlite'`, `transaction: false` (Drizzle's async transactions on bun:sqlite do not roll back). Only `db/` and `schema.ts` know it is SQLite, as now.

Actors: `'user'` becomes `'user:<userId>'`; `'agent:<id>'` is unchanged. Justification: `createdBy`, `assignees` and `projects_members.actor` must say which person once there are several, and a prefixed string keeps one column for humans and agents (no second `userId` column, `json_each` filters unchanged). `isActor` (`packages/shared/src/actors.ts:5`) accepts `user:[a-z0-9]{12}` and the server, never the client, fills the actor from the connection. The bare `'user'` is rewritten once at bootstrap (f) and is then refused.

## (d) Auth flow per surface

- **Browser (server mode).** Better Auth's handler mounted at `/api/auth/*` inside the existing fetch handler (`packages/server-core/src/webui/http-server.ts:306-353` is replaced). `login.html` asks for email and password and keeps `?next=` / `safeNextPath`. The page gate (`http-server.ts:440-450`) and `/api/config` call `auth.api.getSession({ headers })` instead of `validateSession` (`webui/auth.ts:180`). The WebSocket upgrade carries the same cookie (`transport/server.ts:439-442`). `OTTO_WEBUI_PASSWORD` and the jose JWT (`webui/auth.ts:10-89`) are deleted.
- **Electron, local.** No sign-in. Main already mints a per-launch token for the localhost server (`apps/electron/src/main/index.ts:584-586`); the server maps that token to the local user, created on first launch from `preferences.json` name and email (read today by the workspace menu, `workspace-menu.tsx:132-145`). Name and email then live in `users`; the preferences keys and the menu's file read go.
- **Electron to a remote server.** "Connect to a remote workspace" signs in with email and password against `{server}/api/auth/sign-in/email`; the bearer plugin returns the session token, which replaces the shared `OTTO_SERVER_TOKEN` in `RemoteServerConfig.token` (`packages/core/src/types/workspace.ts:15-19`) and travels in the existing handshake `token` (`transport/server.ts:435`). The token is stored with the credential manager, not in `config.json`. The thin client (`OTTO_SERVER_URL`, `preload/bootstrap.ts:60-90`) does the same. `@better-auth/electron` (official since 1.5: system-browser sign-in with PKCE, back through a custom-scheme deep link) is the later step when OAuth sign-in arrives; email and password in-app does not need it. Requests from main send no `Origin`, so Better Auth's origin check does not block them; `trustedOrigins` stays the server origin.
- **CLI and scripts.** `OTTO_SERVER_TOKEN` stays as the machine credential (`packages/server/src/index.ts:9`, `docs/cli.md:43`) and acts as the first admin. Per-user API keys (Better Auth `apiKey` plugin) wait until a second person needs the CLI.
- **Agents.** No credentials. A run's actor is `agent:<id>` in the chat's workspace, set by the server; agent subprocesses talk over stdio, not the WebSocket.

## (e) Authorization

- Roles: workspace `owner` (members, invitations, workspace settings, sources and secrets, delete) and `member` (everything else); instance `admin` (server and provider settings, creating workspaces). Project roles (`projects_members.role`) stay data only. No viewer role until someone asks.
- One place: the handshake resolves `{ userId }` (`validateToken` / `validateSessionCookie` return the user instead of a boolean, `transport/server.ts:85-94,430-449`) and `RequestContext` gains `userId` (`transport/types.ts:7-11`). One wrapper around `server.handle` checks, before the handler: the caller is a member of `ctx.workspaceId`, and of the first argument when that argument names a workspace (55 of the 241 handlers take an explicit `workspaceId`, e.g. `handlers/rpc/pages.ts`, `sources.ts`, `automations.ts`); channels listed in one `OWNER_CHANNELS` / `ADMIN_CHANNELS` set need that role. Handlers stay unaware; domain functions keep taking `workspaceId` first and never see users.
- Isolation: the handshake `workspaceId` (`transport/server.ts`, client-supplied) and `window:switchWorkspace` (`handlers/rpc/workspace.ts:85-89`) are refused without membership; `workspaces:get` returns only the caller's workspaces; pushes already target a workspace. `workspaces:create` takes a server path from the client (`workspace.ts:42-53`): admin only, and in server mode only under `CONFIG_DIR/workspaces`.
- Everything in a workspace is shared by its members except chats, which belong to the user who created them (see Owner direction, phase 3).

## (f) Migration

- Nothing is renamed or moved on disk; `workspaceId` values are unchanged.
- **Server.** With no user in the table, `/login` shows "Create the owner account", which asks for no token (since 2026-10-06; `OTTO_OWNER_EMAIL` restricts who may claim a fresh exposed install). A `databaseHooks.user.create.before` allows a sign-up only then, or for an email with a pending invitation; `emailAndPassword.disableSignUp` stays off because invitations need it.
- **Bootstrap** (`initOwner`, one SQLite transaction, idempotent): sets `admin`, adds an `owner` row for every registered workspace, rewrites `'user'` to `'user:<id>'` in `library.createdBy`, `projects_members.actor`, `tasks.createdBy`, `tasks.assignees`, `timesheets.createdBy`.
- **Electron local:** the same bootstrap with the local user on first launch.
- Remote workspace entries holding the old shared token prompt for sign-in once.

## (h) Open decisions (recommended answer)

1. Organization plugin or our own two tables? **Own tables.** The plugin would give invitations (48 h default), `owner/admin/member`, `session.activeOrganizationId`, teams and `createAccessControl`, but it needs its own `organization` row (unique `slug` required) that duplicates the config registry, its operations are HTTP endpoints keyed on the cookie session while ours run over the WebSocket with a per-connection workspace, and two roles do not need an access-control layer. Revisit if the registry moves to SQLite and we want its invitation endpoints as they are.
2. Roles? **`owner` and `member` per workspace, plus one instance `admin` flag.** No viewer, no admin role.
3. Actors? **`'user:<id>'`**, legacy `'user'` rewritten to the first owner at bootstrap.
4. Keep `OTTO_SERVER_TOKEN`? **Yes, as the machine and CLI credential** (no longer the bootstrap proof); drop `OTTO_WEBUI_PASSWORD`.
5. Desktop local login? **None**; local token maps to the local user.
6. How do people join? **Invitation link, copied by the owner; no email until a mail sender exists.**
7. Private chats per user? **Yes (owner decision)**: a chat belongs to its creator, even owners do not see others' chats.
8. Password reset without mail? **The admin makes a one-time reset link** (later; until then the CLI with the server token).
9. `users.name` vs. our `title` rule? **Keep `name`** and list it as an exception.

## (i) Risks

- 55 handlers read a client-supplied `workspaceId` argument; the guard must cover them all or a member of one workspace reads another. The channel-table test is the control.
- Global state outside workspaces (preferences, LLM connections, server settings in `~/.otto`) is per install, so members share it; anything personal stored there leaks across users. The file channels no longer expose `~/.otto` secrets, other workspaces or other members' chats ("Private paths" under phase 2); agent subprocesses and their shells no longer inherit the server environment (`agentEnv`, an allow-list: the server's secrets, `ENCRYPTION_KEY` included, are never in an agent's env); still open: agent shell execution can read whatever the server user can read (`llm-connections`/OAuth channels and `settings` writes are guarded since P1c and P1a).
- Better Auth moves fast (1.5 split adapters and api-key into packages and replaced its CLI; 1.7 tightened Electron schemes and adapter methods). We use the core and the bearer plugin only, pinned, and upgrade on purpose.
- bun:sqlite with the Drizzle adapter is not named in Better Auth's docs; the adapter code should work with it, but phase 1's first test must prove it.
- First admin: Better Auth has no "first user is admin"; the `databaseHooks.user.create.before` gate is our own code and must be tested against races (two first sign-ups).
- An exposed server between upgrade and first sign-up: closed by `OTTO_OWNER_EMAIL`; without it the first sign-up wins (the boot log warns).
- Cookies behind the getbb.app proxy: set `BETTER_AUTH_URL` to the https public URL (cookies become `Secure`), leave `advanced.trustedProxyHeaders` off (the 1.7 default) and set `advanced.ipAddress.trustedProxies` to the proxy, otherwise rate limiting keys on the proxy address or trusts a spoofed `X-Forwarded-For`. The page and the WebSocket must share one origin or the cookie does not reach the upgrade (`OTTO_WEBUI_WS_URL`, `packages/server/src/index.ts:23`).
- The actor rewrite touches JSON (`tasks.assignees`); one transaction, test with real rows.
